# Второй этап браузерной авторизации

Начиная со следующего выпуска браузерный API `evrasia.rest` поддерживает дополнительное подтверждение входа шестизначным кодом приложения-аутентификатора.

Сценарий взят из сетевого архива владельца `Browser-Network-20261026-031155.zip` (файл содержит закрытые данные; в репозиторий не загружать).

1. `GET /signin/` — получение Bitrix `sessid` и cookies.
2. `POST /bitrix/services/main/ajax.php?…mode=class&c=eurasia%3Asignin&action=process` — прежние поля авторизации `USER_LOGIN`, `USER_PASSWORD`, `AUTH_FORM`, `TYPE`, `BY`, `USER_REMEMBER`, `backurl`.
3. При `status=success, data.otpRequired=true` открывается окно с запросом шестизначного кода. В ответ отправляется только `OTP` через тот же хост и тот же контекст cookies: `POST /bitrix/services/main/ajax.php?…filterState=otp&mode=class&c=eurasia%3Asignin&action=otp`.
4. После `status=success, data.authenticated=true` выполняется контрольный `GET /account/`. Только после подтверждения доступа сохраняется отметка браузерной сессии и продолжается прежняя операция получения сведений о картах или истории.
5. Неверный код предлагает повторный ввод с текстом ошибки; после пяти попыток начальную авторизацию нужно повторить. При отмене код не отправляется; браузерная операция завершается без сохранения новой сессии.

Поле `OTP` не записывается в AsyncStorage, в журнал действий или в сообщения об ошибках. Ожидание кода не затрагивает независимый токеновый API `evrasia.spb.ru/api/v3`. Одновременные попытки браузерной авторизации одного аккаунта объединяются, для разных аккаунтов запрещён параллельный вход во избежание смешения cookies.

Ответы `emailRequired` и `smsRequired` не принимаются за успешный вход: приложение объясняет, что этот вариант подтверждения пока не поддерживается.

Точный формат и порядок запросов из сетевого архива подтверждены; испытание на реальном устройстве требуется отдельно.
