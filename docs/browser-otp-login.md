# Браузерная авторизация и получение PIN (v17)

## Авторизация аккаунта

- При добавлении аккаунта и ручной повторной авторизации сначала выполняется существующий мобильный вход, затем вход через `evrasia.rest`. При ответе `otpRequired: true` показывается окно шестизначного кода.
- Cookies браузерного API отделены по аккаунтам и сохраняются в `expo-secure-store` в формате версии 2. Прежний строковый маркер `browser-cookie-session` из v16 не принимается за действующую сессию.
- HTTP-запросы браузерного API выполняет нативный `BrowserSessionModule` (HTTPS, собственный cookie jar в аргументах запроса, сохранение Set-Cookie, ограничение перенаправлений доменом evrasia.rest); параллельные запросы одного аккаунта последовательно обрабатываются.
- Действительной сессия считается только после успешного ответа `authenticated` и подтверждения доступа к `/account/`. При отмене второго фактора аккаунт не считается полностью авторизованным.
- История и сведения о картах **не запускают новый вход**; они используют сохранённую сессию, а при её отсутствии/истечении требуют ручной повторной авторизации аккаунта.

## Получение PIN-кода

- В настройках появился общий переключатель «Способ получения кода списания», сохраняемый между запусками. Значение по умолчанию: `mobile`.
- `mobile`: прежний запрос `POST https://evrasia.spb.ru/api/v3/pincode`, ожидание и обработка SMS.
- `browser`: из существующего `/account/` извлекается Bitrix `sessid`; выполняется `POST https://evrasia.rest/local/php_interface/pincode.php`, тело `sessid=…`. Ответ `status=success, pincode` содержит четырёхзначный код, который отображается и копируется сразу, без разрешения на получение SMS.
- Формат буфера обмена: `чекин: XXXXX, на списание: XXXX`. PIN-код не сохраняется в журнале приложения.
- Отсутствующая/истёкшая браузерная сессия не заменяется незаметной авторизацией: выводится сообщение о необходимости повторного входа.

Сетевые записи владельца использованы только для определения протокола (`Browser-Network-20261026-031155.zip`, `Browser-Network-20261026-034309.zip`); закрытые данные и архивы в репозиторий не добавлены.

## Проверка

Подтверждается сборка APK в GitHub Actions. На телефоне проверить: добавление аккаунта с TOTP, повторный вход, использование истории без нового запроса TOTP, оба режима получения PIN, переключатель после перезапуска, изоляцию двух аккаунтов и сохранение cookies после перезапуска.

## Восстановление браузерной PHP-сессии (v18)

Реализован механизм по исследованию `Evrasia_Bitrix_Session_Refresh_Research_2026-10-26.md` (пользовательский файл, **не** добавлять исходные сетевые архивы в репозиторий).

- В HTML действительного `/account/` ищется `bxSession.Expand('k')` — ключ из двух шестнадцатеричных сегментов 32 и 64 знака — и существующий Bitrix CSRF. Значения хранятся с cookie-состоянием **каждого** аккаунта только в SecureStore, не попадают в журнал.
- При обращении к истории, картам или браузерному PIN выполняется проверка `/account/`. Если сервер явно вернул страницу входа или ошибку авторизации, приложение делает **одну попытку** восстановления: `GET /bitrix/tools/public_session.php?k=…` с сохранёнными долговременными cookies и `X-Bitrix-Csrf-Token`. При восстановлении из запроса исключается **только** старый `PHPSESSID`. Ключ `k` не синтезируется и не выводится из CSRF.
- Все `Set-Cookie`, в том числе выдача нового `PHPSESSID`, продление сроков и `Max-Age=0`, обрабатываются существующим нативным хранилищем. Дополнительно сохраняется атрибут `HttpOnly`.
- Только ответ `SESSION_CHANGED` разрешает контрольный запрос `/account/`. Рабочая страница — признак восстановленной сессии. `SESSION_EXPIRED`, неизвестный ответ, отсутствие `k`/CSRF или отказ авторизации требуют обычного ручного входа с 2FA.
- Сетевая ошибка и HTTP 5xx не удаляют авторизацию и допускают повторную проверку позднее; нет бесконечных запросов, таймеров или постоянной фоновой активности. Параллельные попытки восстановления одного аккаунта объединяются.
- До запроса браузерного PIN обязательно выполняется проверка/восстановление. Запрос `pincode.php` **никогда не повторяется автоматически**, даже после неясного ответа сервера.
- Вход и запрос кода 2FA при создании/ручной авторизации аккаунта сохраняются, поведение истории и PIN не приводит к скрытому логину. Мобильный API и переключатель способа PIN не менялись.

**Ограничения доказательств.** В исходной сетевой записи подтверждено одно восстановление `PHPSESSID` без повторного ввода данных, но неизвестно, какие cookies минимально необходимы, как долго действует ключ `k`, когда отзываются долговременные cookies и всегда ли восстановление возможно. Модуль не обещает автоматическое восстановление в этих случаях.

**Приёмка на устройстве:** работоспособная сессия без дополнительного входа; отсутствие только `PHPSESSID`; перезапуск с долговременными cookies; `SESSION_EXPIRED`; отсутствие параметра `k`; сетевой сбой; отсутствие дублированного запроса PIN; несколько аккаунтов; отсутствие секретов в журнале.
